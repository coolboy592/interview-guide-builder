# 黄金样例参考：原文与起草方法

> **来源声明**：以下样例文本来自 akashic-agent 项目（「工具发现与上下文管理」章），仅示范风格、密度与格式。新项目必须用自己的事实产出自己的样例，**不得复用其内容**。

## 1. 为什么样例先行（思考方式）

- 规则传达不了语感与密度：几十条禁令写不出"好的导语念起来是什么节奏"，一段样例可以。
- 规则以禁止项生长不会收敛：正向样例给执行者和用户一个共同的参照物，验收争议对着样例裁决。
- 样例是整个规格的锚点：它同时锁定导语的节奏、支撑内容的深度标尺、符号处理与链接格式。样例认可了，规格才算定稿；所以**先定稿样例、再铺开问题稿**。

## 2. 样例选取标准

一段导语节选（覆盖叙事的前两段即可，不必整篇）＋ 一两条支撑内容符号条目 ＋ 链接格式示例。选材挑最能代表本项目讲述风格、事实最扎实的片段。

样例中的**追问样例**须覆盖本项目两类最高价值的回答——至少一条**算法选择／设计评价**回答（如损失方向选型、奖励设计评价：含记录事实、当时判断（可标未知）、现在复盘、证据边界四层）与一条**工程机制**回答（如某机制为何成立：含机制、手段、代价、边界）；不以故障排障类回答单独代表全书。样例中至少一次实际示范三层标注（记录事实／当时判断／现在复盘）的写法。

## 3. 起草步骤

1. 选最容易偏移的问题（打样问题），取其资料索引中最有讲述价值的素材（优先"背景动机＋判断"或"设计评价"——最能体现项目思考密度的片段）；
2. 对照 00-README 硬性标准写：第一人称、句式完整可直接口述、无生活化比喻、符号 ≤3 且首现括注；评价类内容守住"有依据的评价 ≠ 因果定论"；
3. 交用户**逐句认可**——"语感不对"是有效否决理由，改到认可为止，不讨价还价；
4. 嵌入工作区 00-README 的"黄金样例"节；后续所有问题稿以它为风格与密度锚点。

## 4. akashic 原文（风格参考）

### 4.1 口述层（节选：背景与卡点 → 我的判断）

> 项目初期只有少量本地工具，全部工具 Schema 随每个请求下发，成本可以忽略。接入 MCP、注册工具增长到几十个之后，出现两个直接问题：其一，工具定义与对话历史竞争同一个上下文窗口，每轮请求都要为全部工具的名称、描述和参数结构支付 token；其二，provider 对单个请求可携带的工具数有硬性上限，全量注入直接触碰限制。调试中还暴露出一个更隐蔽的缺陷：模型已经"知道"某个工具存在并尝试调用，却因为该工具的 Schema 没有进入本轮请求而调用失败——系统把"注册过的工具"和"本轮可调用的工具"当成了同一件事。
>
> 我的判断是，这不该靠继续扩大上下文窗口解决，而是缺少一个显式的投影层：注册表保持完整，每轮请求只携带一个受容量约束的可见工具集合；未进入集合的工具放进可搜索的目录，模型按需检索、当轮解锁后进入后续请求。这把"能力总量"与"单轮可见性"解耦，代价是引入一次工具发现交互和跨请求的投影状态管理。这个交换在工具规模大、单任务只使用其中小部分的场景下成立；工具少且稳定的项目，全量注入仍是更简单的正确选择。

值得注意的风格要素：现象与代价先于架构；判断段里写明代价与适用边界（"工具少且稳定的项目，全量注入仍是更简单的正确选择"），不弱化替代方案。

### 4.2 支撑层·关键机制详解（条目格式：符号——作用）

> - `tool_search`——注册表内的元搜索工具：模型用名称或关键词在工具目录中定位工具；自身必须常驻可见集合，否则发现入口不可达。
> - `max_tool_schemas`——provider 对单请求工具数的硬上限：可见投影据此裁剪，当轮解锁的新工具优先占用被淘汰的旧预加载工具的槽位。
> - `CommittedContextUnit`（已提交上下文单元）——压缩的最小完整交互单位：覆盖用户消息、assistant 发起的整批工具调用与全部对应结果，批次闭合前不可提交，保证压缩不会从协议中间切断。

格式要素：每个符号首现紧跟一句作用说明；解释写边界与例外（"否则发现入口不可达"），不是同义反复。
